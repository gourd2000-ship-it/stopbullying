# 데이터베이스(DB) 연동 로드맵 (비밀번호 헤더 검증 방식)

기존 로컬 스토리지(`localStorage`) 기반 시스템을 실제 데이터베이스(DB)로 전환하기 위한 로드맵입니다. **공통 기능 -> 개별 기능** 순서로 재구성되었으며, 복잡한 JWT 토큰 방식 대신 구현이 간편한 **단일 비밀번호 헤더 검증 방식**을 적용했습니다.

---

## 1. 사전 분석 및 아키텍처 설계 (CoT 기반 사고 흐름)

### [사고 흐름 1] 공통 기능과 개별 기능의 분리
* **공통 기능**: DB 인프라 설정, 테이블 스키마, 백엔드 DB 연결 객체, 공통 비밀번호 검증 미들웨어, 프론트엔드의 비동기 통신 유틸리티가 이에 해당합니다.
* **개별 기능**: 학생의 상담 내용 저장(Create), 관리자의 데이터 조회(Read) 및 수정(Update) 등 도메인에 특화된 기능들입니다.
* **결론**: 공통 기반을 먼저 다진 후, 학생 페이지와 관리자 페이지를 순차적으로 연동하는 방식으로 진행합니다.

### [사고 흐름 2] 기존 프론트엔드와의 충돌 방지 (동기 vs 비동기)
* **문제점**: 현재 프론트엔드는 `setRecords(db.getConsultations())`처럼 데이터를 동기적(Synchronous)으로 바로 가져와 렌더링하고 있습니다.
* **해결책**: DB 연동 시 데이터 조회가 비동기적(Asynchronous)으로 바뀌므로, React의 `useEffect` 안에서 `async/await`를 사용해 데이터를 불러오고, 데이터를 기다리는 동안 보여줄 '로딩 상태(Loading State)'를 추가하여 기존 렌더링 로직과 충돌하지 않도록 컴포넌트를 리팩토링합니다.

### [사고 흐름 3] 보안 대책 마련 (비밀번호 헤더 검증)
* **보안 방식**: 복잡한 JWT 발급 및 로그인 검증 API 대신, 프론트엔드에서 API를 호출할 때 헤더에 관리자 비밀번호 자체를 실어 보냅니다(예: `x-admin-password`).
* **서버 검증**: 백엔드(서버)는 API 요청이 들어올 때마다 헤더의 비밀번호와 서버 환경 변수(`process.env.ADMIN_PASSWORD`)가 일치하는지만 확인하는 단순 미들웨어를 거치게 하여 무단 접근을 차단합니다.

## 2. 단계별 DB 연동 로드맵

### Phase 1: 공통 기능 (기반 인프라 및 핵심 모듈 구축)
1. **DB 환경 설정 (Supabase 권장)**
   * 프로젝트 생성 및 `consultations` 테이블 스키마 구성.
   * `.env` 파일에 DB 연결 URL 및 안전한 `Service Role Key` 설정.
2. **백엔드 공통 모듈 (`api/`)**
   * DB 클라이언트 초기화 코드 작성.
   * **[보안]** 비밀번호 검증 미들웨어 구현 (요청 헤더의 `x-admin-password`가 `process.env.ADMIN_PASSWORD`와 일치하는지 확인).
3. **프론트엔드 공통 유틸리티 (`src/utils/`)**
   * 기존 `db.ts`(로컬 스토리지)를 폐기하고, 백엔드 API와 통신(비동기 `fetch`)하는 새로운 네트워크 모듈 작성. 
   * 관리자 요청 시 `localStorage`에 저장된 비밀번호를 `x-admin-password` 헤더에 자동으로 포함하여 요청하는 공통 로직 구성.

### Phase 2: 개별 기능 1 - 학생 상담 (저장 기능 연동)
1. **백엔드 API 구현**: `POST /api/consultations`
   * 전달받은 요약 정보와 대화 내역을 DB에 Insert. (학생의 기록 저장은 별도의 비밀번호 검증 없이 허용하되, 비정상적 도배 방지를 위한 최소한의 안전장치 권장)
2. **프론트엔드 연동 (`ChatPage.tsx`)**:
   * 대화 종료 시 요약(Summarize)이 끝난 후 비동기로 DB에 전송. 기존 비동기 흐름을 유지하므로 충돌 없이 자연스럽게 연결 가능.

### Phase 3: 개별 기능 2 - 관리자 기능 (조회 및 수정 연동)
1. **백엔드 API 구현**:
   * `POST /api/admin/login` (선택 사항): 입력한 비밀번호가 올바른지 서버에서 1차 확인해주는 간단한 검증 엔드포인트.
   * `GET /api/consultations` & `GET /api/consultations/:id`: 헤더 비밀번호 검증 미들웨어를 통과한 요청만 DB 데이터를 조회하여 반환 **[보안]**.
   * `PATCH /api/consultations/:id`: 조회 상태 및 메모 업데이트.
2. **프론트엔드 컴포넌트 리팩토링 (충돌 방지)**:
   * `AdminLogin.tsx`: 로그인 성공 시 입력한 비밀번호 자체를 로컬 스토리지에 `admin_password`로 저장.
   * `AdminDashboard.tsx`, `AdminDetail.tsx`: 
     * **로딩(Loading) 상태 추가**: 데이터를 가져오는 동안 UI가 깨지지 않도록 로딩 UI 적용.
     * **비동기 처리**: `useEffect` 내에서 `async` 함수를 사용해 API를 호출하고 `setRecords` 진행. 인증 실패(비밀번호 오류) 시 로그인 페이지로 자동 리다이렉트 처리.

### Phase 4: 최종 테스트 및 배포
1. 로컬 환경에서 비동기 데이터 렌더링 시 기존 UI 깨짐이 없는지 검증.
2. 헤더에 잘못된 비밀번호를 넣거나 헤더 없이 관리자 API 호출 시 정상적으로 차단(401 Unauthorized)되는지 검증.
3. Vercel 플랫폼에 DB 연결 정보 및 `ADMIN_PASSWORD` 환경 변수 등록 후 최종 배포.
